# LXL 联赛管理平台

> 历史文档：以下描述迁移前直接代理原用户系统的版本。独立管理后端上线后，请按根 README 和 backend/README.md 发布，勿用此处旧脚本覆盖当前代理。

独立的管理员前端项目。与 `../lxlleague` 同级，拥有自己的依赖、构建和部署流程；不导入原仓库源码、不直接连接数据库、不执行数据库迁移。业务接口暂时由现有系统提供，旧后台保留。

## 技术栈

React 19、TypeScript、Vite 7、Ant Design 6、React Router 7、TanStack Query 5。接口请求使用原生 fetch，登录态由业务服务签发 HttpOnly Cookie；不把密码或令牌写入 localStorage。页面模块按路由懒加载。

### 大屏选人迁移

在“常规赛事”列表进入“大屏选人”，地址为 `/draft/:id`，兼容 `/admin/pick/:id`。复用原 1.0 的完整操作界面，独立全屏展示。选满后“保存并查看对阵”进入本后台 `/matches/:id/lineup`，核对后可单独确认“结束选人并开赛”。开赛继续调用原业务服务的校验和赛程生成逻辑。

选人操作实时写入原业务服务；刷新会恢复已写入的名单。退出或浏览器返回时，存在本次编辑会提示保存草稿、继续编辑或清空；“不保存并清空”会调用原丢弃草稿接口，清除队伍和选人，保留报名。刷新/关闭标签时使用浏览器离开提示。开赛、清空、操作和查看分别使用 `draft.finish`、`draft.reset`、`draft.control`、`draft.view` 权限；现有三级管理员维持原 1.0 权限范围，可由服务端清单进一步收紧。

仅迁移 1.0。新后台不包含 2.0 竞拍组件；旧 `/admin/auction/:id`、`/auction/:id` 地址显示停用提示并引导到 1.0。原项目已撤下 2.0 入口，旧页面地址重定向至原 1.0；其组件、业务接口和数据暂留作回退，待迁移确认后再清理。

**部署顺序：先更新原业务服务，再更新本后台。** 原仓库新增 `GET /api/admin/draft/music`，并为 `/api/admin/permissions` 增加四个 `draft.*` 权限，无数据库迁移。若服务器已有旧版权限接口但未更新四个权限，新后台会拒绝选人，需部署新版后端；不会把“缺少权限”当作旧接口回退。音乐接口明确 404 时兼容两首原有曲目，其他错误显示重试提示且允许继续选人。

图片、段位、队标及音乐继续经 `/assets/` 代理访问原业务服务。后台构建包不复制原来的 MP3；部署时需保留原 `public/assets/music/` 和其他媒体目录，不能随旧页面一并删除。

商品管理支持头像框、称号、铭牌、背景和通用道具，内置样式目录保存在本项目 `src/data/`，图片资源通过现有 `/assets/` 代理访问，不依赖原仓库源码。上传支持 JPG、PNG、GIF、WebP、SVG，最大 5MB；文件真实性和 SVG 清理由原上传服务校验。上传完成后需保存商品才关联图片。现有创建接口默认上架且不限库存，创建后可编辑库存和上下架状态。0 币商品必须设置领取资格。已有商品保持原分类和专用道具效果；删除使用已有软删除接口，不移除用户已购背包记录。

充值入口为 `/recharge`，也可从商品管理页进入。沿用核心管理员接口 `/api/admin/points/recharge`，仅增加冠军币余额，不接入外部支付。用户搜索遵循原管理用户接口的权限范围，当前登录账号不在候选中。确认弹窗展示账号、UID、游戏 ID、金额和备注；同一次提交禁止重复点击、不自动重试。网络中断或服务器错误导致结果不明时，会阻止当前页面重复提交，须先通过用户到账通知或原系统流水核实，再重新填写。该保护限当前页面，不替代后端幂等控制。充值结果仅展示本次响应，不伪造历史流水；真实账本和到账通知由原业务服务在事务内写入。

竞猜管理入口为 `/markets`，沿用原后台的核心管理员界面限制。自动赔率、开盘 15 分钟截止、比分触发自动结算及冠军币账务仍由现有后端负责，新后台只调用已有接口。开盘、封盘、重开、手动结算和作废均需确认。下注明细接口最多返回最近 1,000 笔，页面明确标注统计范围；列表与打开的明细每 10 秒刷新。

工作台的“可管理用户”遵循原接口权限范围并排除当前账号；“未结束赛事”包含待选人和进行中的常规赛。“报名管理”接口仅返回仍在报名/待选人阶段的赛事报名，不是全部历史记录。所有时间显示为北京时间。

## 本地运行

### 权限接口兼容

新后台登录后读取 `/api/admin/permissions` 的权限清单，菜单、路由和按钮统一通过 `can()` / `Permit` 判断，并叠加目标账号约束。明确返回 404 时兼容旧后端三级角色；401/403、异常或无效响应不会回退放宽权限。已有角色的权限上限继续保留，服务端返回收紧后的权限会进一步限制界面。

角色目前固定为普通/二级/核心管理员，本次不包含自定义角色的勾选授权存储或编辑页。角色设置入口位于用户管理每行的“设置角色”，仅核心管理员可用；业务条件不满足时按钮禁用并显示原因。用户删除需输入目标账号二次确认。

同级 `lxlleague` 已补充权限查询接口并修复无效角色默认为普通用户的问题，部署详情见该仓库 `docs/独立后台权限接口.md`；无需数据库迁移。用户管理写操作使用已有 POST 接口，最终权限和状态检查由业务服务执行。

使用 Node.js 24 LTS 和 npm。

```powershell

npm ci
Copy-Item .env.example .env
npm run dev
```

访问 `http://127.0.0.1:5174`。默认代理到 `http://127.0.0.1:3000`，需要原项目的本地业务服务已经运行。请自行选择开发/测试数据库；本项目不会读取或复制原仓库 `.env`，也不会自动启动原服务。

开发代理地址只写在服务端环境变量 `BACKEND_ORIGIN`，不进入浏览器构建。`/api/` 和 `/assets/` 代理到业务服务。前端构建资源使用 `/static/`，避免与原系统媒体资源冲突。

生产业务服务使用 `__Host-` + Secure Cookie。若本地要接入生产模式的服务，管理端预览也必须使用正确的 HTTPS 环境；不要通过移除 Cookie 安全属性绕过这一限制。默认本地 HTTP 代理适用于原服务的开发模式。

连接生产接口时，将本地 `.env` 中的 `BACKEND_ORIGIN` 设为 `https://lxlleague.cn`，并同时设置 `DEV_HTTPS_KEY` 和 `DEV_HTTPS_CERT` 为本地证书私钥与证书文件路径（例如 `.certs/localhost-key.pem`、`.certs/localhost.pem`）。证书需覆盖 `localhost` 和 `127.0.0.1`。重启 `npm run dev` 后访问 `https://127.0.0.1:5174`。若使用自签名开发证书，浏览器首次访问需确认该本地证书；`.certs/` 已排除出 Git。此模式中的管理操作会修改生产数据，登录仍使用有管理权限的真实账号。

## 独立部署

### 阿里云宿主机 Nginx 部署

当服务器无法拉取 Docker 镜像时，可以使用系统软件源安装 Nginx。上传预构建部署包及 `deploy/stage-host.sh` 后，以 root 执行 `bash stage-host.sh /path/to/lxlleague-admin.tar.gz`。脚本将静态文件放在 `/opt/lxlleague-admin/releases/`，通过 `current` 符号链接选择版本，并配置仅本机可访问的 `127.0.0.1:8081` 服务与生产 API 代理。脚本面向 Alibaba Cloud Linux 的 Nginx 和 CA 证书路径。

本次服务器公网 IP 为 `8.133.23.125`，访问入口为 `https://8.133.23.125`，业务接口代理至 `https://lxlleague.cn`。`deploy/ip-http.conf` 提供 HTTP 证书验证入口，`deploy/ip-https.conf` 提供 HTTPS 反向代理。两者复制到 `/etc/nginx/conf.d/` 时，HTTPS 配置必须等待证书签发完成后再启用。阿里云安全组需允许公网 TCP 80、443 入站，8081 仅绑定回环地址。

无域名时，使用 Certbot 5.4 或更高版本为公网 IP 申请 Let's Encrypt 短期证书：

```sh
/opt/certbot/bin/certbot certonly --non-interactive --agree-tos \
  --register-unsafely-without-email --preferred-profile shortlived \
  --webroot --webroot-path /var/www/acme \
  --ip-address 8.133.23.125 --cert-name 8.133.23.125
```

`deploy/certbot-renew.service` 和 `.timer` 复制到 `/etc/systemd/system/`，`deploy/reload-nginx.sh` 复制到 `/opt/lxlleague-admin/` 并赋予执行权限，然后执行 `systemctl daemon-reload`、`systemctl enable --now certbot-renew.timer`。定时器每天检查两次续期，成功后校验并重载 Nginx。签发后执行 `certbot renew --dry-run` 验证续期链路。证书与私钥仅保存在服务器 `/etc/letsencrypt/`。

回退静态版本时，将 `/opt/lxlleague-admin/current` 指向需要恢复的历史 release 目录，再执行 `nginx -t && systemctl reload nginx`。此部署不执行数据库迁移。

### Docker 部署

对于内存较小的服务器，可先在本地执行 `npm ci`、`npm run build`，再上传 `dist/`、`deploy/` 和 `compose.prebuilt.yml`。在服务器项目目录中将 `deploy/production.env.example` 复制为 `.env`，执行 `docker compose -f compose.prebuilt.yml up -d --build`。此方式仅在服务器构建 Nginx 静态镜像，不运行 Node.js 构建；HTTPS 入口配置仍按下述步骤处理。不要上传本地 `.env`、`.certs/` 或 `node_modules/`。

1. 新增后台域名和 HTTPS 证书，例如 `admin.example.com`。
2. 在新后台项目 `.env` 中配置 `BACKEND_ORIGIN=https://现有业务域名`（不带路径、末尾不带 `/`）。这是服务器配置，不是浏览器接口地址。
3. 执行 `docker compose up -d --build`，默认仅绑定本机 `127.0.0.1:8081`。
4. 参考 `deploy/tls-proxy.example.conf` 给宿主机反向代理增加独立后台虚拟主机，保留用户站点配置。
5. 经 HTTPS 后台域名验证登录、退出、权限、筛选、分页及实际写操作。

容器只含静态前端和 Nginx，不包含数据库、业务后端或会话密钥。若代理同机容器中的业务服务，需配置可达的地址或显式加入其 Docker 网络；容器内的 `127.0.0.1` 指向容器自身。

### 登录与 CSRF 代理约定

- 浏览器只向后台自己的域名发送 API 请求；后台 Nginx 再转发到业务服务。
- 业务响应中的 Host-only 会话 Cookie 留在后台域名。用户端登录与后台登录相互独立。
- 不改写浏览器 `Origin` 和 `Sec-Fetch-Site`。代理将 `X-Forwarded-Host` 设为后台真实 Host，使原服务对同源写操作校验通过，同时保留对外部来源的拒绝。
- 宿主机 TLS 入口必须覆盖 `Host`、`X-Forwarded-Proto`、`X-Real-IP`；不能直接信任客户端传入的同名头。Compose 仅暴露 loopback 端口，避免绕过可信入口。
- 若现有业务服务前还有一层网关，需确认它不会把 `X-Forwarded-Host` 强制改回用户站点域名。优先让后台代理直接访问已有应用的内部入口；这一步属于部署联调，不能仅靠前端构建证明可用。
- 不开启通配 CORS，不共享父域 Cookie，不复制会话签名密钥。实际操作权限继续由原业务服务强制校验。

## 上线验收与回退

先在测试数据上核对接口与权限，再对生产环境做受控验收。重点验证未登录、普通用户、普通/二级/核心管理员的权限边界、账号审核、比赛创建、跨源报名 ID、上下架及退出后访问保护。

完整赛事流程尚未迁移，在新后台覆盖实际运营需求、验证稳定并具备回退路径之前，继续保留原后台。后续清理原后台页面时也必须保留新系统仍依赖的 API、鉴权和业务服务。
